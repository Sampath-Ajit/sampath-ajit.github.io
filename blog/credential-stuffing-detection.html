Your "Failed Login" Alert Is Lying to You

A credential-stuffing rule that doesn't cry wolf — built on behavioral signatures, proven both ways.

Aug 2026·5 min read·Field Report 002

Most teams' first detection rule looks like this: "Alert on 5 failed logins."

It fires constantly — every user who forgets a password trips it. Within a week, analysts mute it. Now you're paying for a SIEM that nobody watches, which is functionally the same as having no SIEM.

This is the false-positive trap. But there's an equally deadly opposite: tune so aggressively for "real attacks" that quiet, low-and-slow stuffing campaigns sail through — the false-negative trap.

Good detection engineering means low false positives AND low false negatives at the same time. Here's how I built and proved such a rule for credential stuffing, end to end.

Step 1: Reason about the behavior before touching the tool

What actually distinguishes credential stuffing from everything else that produces failed logins?

PatternFailed loginsUsernamesSource IPWindow
Confused real userA fewOne (their own)OneAny
Password reset stormSeveralOne each, self-targetedDistributedMinutes
Brute force one accountManyOneOneShort
Credential stuffingManyMany distinctOneTight

The stuffing signature isn't "many failures" — it's many distinct usernames failing from a single source in a tight window. Attackers run leaked username:password pairs against your login endpoint; each pair fails once or twice, but thousands of different usernames cycle through one machine.

That insight is the whole rule. Everything else is implementation.

Step 2: Build it in Elastic

With Fulcrum's logs shipping into Elasticsearch via Filebeat, the rule is a Threshold rule in Kibana (Security → Rules → Create new rule → Threshold):

  • Custom query: event.action: "login_failed"
  • Group by: source.ip
  • Cardinality threshold: count of distinct user.name ≥ 10
  • Window: 1 minute

Note what the rule does not key on: a raw failure count. Grouping by source IP and counting distinct usernames encodes the behavioral signature directly — one confused user retrying their own login five times can never reach ten distinct usernames, no matter how fast they type.

Step 3: Test against BOTH patterns — the part everyone skips

A rule you haven't fired is a hypothesis, not a control. I generated both traffic patterns with curl and watched Kibana.

Attack pattern — should fire (10 distinct users, one source)

for u in alice bob carol dave erin frank grace heidi ivan judy; do
  curl -s -X POST http://localhost:3000/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"$u\",\"password\":\"wrong\"}"
done

Benign pattern — must NOT fire (one confused user)

for i in 1 2 3 4 5; do
  curl -s -X POST http://localhost:3000/login \
    -H "Content-Type: application/json" \
    -d '{"username":"real_user","password":"wrong_attempt_'$i'"}'
done

Results:

  • ✅ Stuffing pattern → alert fired within the window, grouped by the attacking IP
  • ✅ Benign pattern → silence. No alert. No analyst pinged for nothing.

Both outcomes recorded in a detection-tuning log — because six months from now, when someone asks "why does this rule exist and can we trust it?", the answer should be documented evidence, not folklore.

The meta-lesson

Notice the workflow: threat behavior → signature reasoning → rule encoding → adversarial test → benign test → documentation.

The tool was Elastic. It could have been Splunk, Sentinel, or anything else — the discipline transfers unchanged. Tools don't make detection engineers; the loop does:

  • Ask what makes this attack behaviorally unique?
  • Encode exactly that — nothing more, nothing less
  • Prove it fires on attack traffic
  • Prove it stays silent on normal traffic
  • Write down what you did

Do that consistently and your SOC stops drowning in noise it ignores — and starts catching campaigns it would have missed.
