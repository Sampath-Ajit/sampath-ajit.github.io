I Planted a BOLA Vulnerability in My Own API — Then Fixed It the Right Way

Why the top OWASP API risk survives even code that "does everything right."

Aug 2026·5 min read·Field Report 001

BOLA — Broken Object-Level Authorization — sits at #1 on the OWASP API Security Top 10 for a reason. It's the vulnerability behind some of the largest data leaks of the last decade, and it consistently survives code review, SAST scans, and penetration tests that only check "is this endpoint authenticated?"

Authentication answers who are you? Authorization answers is this yours? Most BOLA bugs exist because a team answered the first question and assumed that settled the second.

To prove how small the gap is, I built an API with a deliberately planted BOLA flaw as part of my AppSec research lab (Fulcrum, a deliberately vulnerable polyglot microservices application), exploited it with a single curl, and then fixed it properly. Here's the whole story.

The vulnerable endpoint

Here's an invoice endpoint from Fulcrum. Spot the problem:

// Before (vulnerable):
app.get('/invoices/:id', authenticate, async (req, res) => {
  const result = await pool.query(
    'SELECT * FROM invoices WHERE id = $1',
    [req.params.id]
  );
  if (!result.rows[0]) return res.status(404).end();
  res.json(result.rows[0]);
});

Read it like a reviewer would:

  • ✅ Requires authentication (the authenticate middleware verifies the JWT)
  • ✅ Uses parameterized queries — no SQL injection
  • ✅ Returns 404 for missing objects
  • ❌ Never asks whose invoice it is

The query fetches any invoice by ID. The JWT got you in the door; after that, the API will happily hand you strangers' financial records.

The exploit is embarrassingly boring

# As User A, request User B's invoice:
curl -H "Authorization: Bearer <user_A_token>" \
     http://localhost:3000/invoices/<user_B_invoice_id>

That's it. No injection, no crypto break, no privilege escalation chain. Just change an ID. If IDs are sequential integers, an attacker doesn't even need to guess — they enumerate. This is exactly how mass data-scraping incidents happen against production APIs.

The fixes that don't fix it

Before showing the real fix, three "fixes" I see teams reach for that fail:

  • "Use UUIDs instead of sequential IDs." GUIDs are unguessable-ish, not secret. They leak in referrals, logs, browser history, other endpoints. Security by obscurity with extra steps.
  • "Strip fields from the response." Removing owner_id from the JSON changes nothing about who can fetch the object.
  • "Check authorization on the frontend." The frontend is under the attacker's control. Always.

The actual fix: bind ownership into the query

The minimal structural fix is to make ownership a filter on the data access itself, using an identity taken from the verified token — never from anything client-supplied:

// After (fixed):
app.get('/invoices/:id', authenticate, async (req, res) => {
  const result = await pool.query(
    'SELECT * FROM invoices WHERE id = $1 AND owner_id = $2',
    [req.params.id, req.user.sub]   // sub = subject claim from jwt.verify()
  );
  if (!result.rows[0]) return res.status(404).end();
  res.json(result.rows[0]);
});

Three properties make this correct:

  • The identity comes from the server-verified JWT (req.user.sub, populated by jwt.verify() in the auth middleware). A client can only present tokens we signed.
  • Ownership is enforced at the data layer. There is no code path where an object is fetched and ownership checked "afterward" — if you don't own it, the row simply doesn't exist for you.
  • It fails closed with a 404, not a 403. Confirming an object exists but belongs to someone else is itself information leakage. 404 keeps the enumeration blind.

Verify like an attacker, not a developer

A fix isn't a fix until it's reproduced against:

docker compose up --build -d

# Two different users' tokens via /login, then:
curl -H "Authorization: Bearer <user_A_token>" \
     http://localhost:3000/invoices/<user_B_invoice_id>
# → 404, not User B's data. ✔

Then re-run an authenticated DAST scan (OWASP ZAP, logged-in context) against the fixed build and confirm the finding no longer surfaces. Document before/after. "Should be fine now" is not a remediation state.

The takeaway checklist

For every endpoint that returns or mutates an object by identifier:

  • Where does the identity used for the access decision come from — verified token, or client input?
  • Is ownership part of the query itself, or a check bolted on after fetching?
  • Does a cross-tenant request return 404 (blind) rather than 403 (leaky)?
  • Do your automated tests include User A requesting User B's object as a negative case?
  • Do your DAST scans run authenticated, where BOLA actually lives?

BOLA isn't exotic. It's a one-line omission with org-wide blast radius — and a one-line fix away from dead.
